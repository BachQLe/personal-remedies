# Item overlay audit — for Sunny and Mory

**This is a plain-language guide, not an engineering doc.** It explains what
the "item overlay" is, why it exists, exactly what to type into which file,
and which items to do first. Every number below came from actually running
`node scripts/audit-overlay.mjs` against the real data on 19 Sep 2026 — none
of it is estimated. (First written 06 Sep 2026, when only isBeverage/isSnack
existed; updated now that isBreakfast has been added and all three flags are
live in the Plan screen.)

If you want the raw, unrounded numbers behind any claim in this doc, re-run
that command yourself (see "Re-running this audit" at the bottom).

---

## 1. What is "the overlay," and why does it exist?

Remedi gets its food data from a vendor called Nutridigm. For every food
item (about 1,485 of them), Nutridigm tells us its name, its food group,
and how it's described — but it does **not** tell us three things the app
needs:

- **Is this a snack?** ("Snacks & Sweets" is a Nutridigm food group, but
  that group also contains things like Honey, Molasses, and pie crust —
  ingredients you'd never eat on their own. Meanwhile real snacks like nuts
  and fruit live in totally different Nutridigm groups.)
- **Is this a beverage?** Nutridigm has a "Beverages" group, but drinks also
  hide inside other groups — orange juice lives in "Fruits," almond milk
  lives in "Nuts & Seeds," and iced tea-type items can live almost anywhere.
  Nutridigm's own grouping can't tell the app "this is something you drink."
- **Is this a breakfast food?** (New.) Nutridigm has no breakfast concept at
  all. A first machine pass tags only the clearest cases — cereal, oatmeal,
  granola, bagels, waffles, pancakes, grits, muffins (in the Breads/Grains
  group) and yogurt/cottage cheese (in the Dairy group) — and deliberately
  leaves fruit untagged, since fruit isn't breakfast-specific and a wrong
  guess puts an odd food in a highly visible spot.

So the app keeps its own small side-file — **the overlay** — that tags
individual items with `isSnack: true`, `isBeverage: true`, or (new)
`isBreakfast: true` (and, in the future, a photo). Two layers make up the
overlay:

1. **`src/data/cache/itemOverlay.generated.json`** — a machine-made first
   pass. A script guesses `isSnack`/`isBeverage`/`isBreakfast` from the
   item's name and group (e.g., anything named "... juice" in the Fruits
   group gets `isBeverage: true`). **You never edit this file** — it gets
   wiped and regenerated by a script.
2. **`src/data/cache/itemOverlay.json`** — **this is your file.** It now
   has 2 entries (Soy milk and Tomato juice — see §7). Anything you add
   here overrides the machine guess for that item. This doc is entirely
   about what to put in here.

The app merges both layers, with your file always winning if the two
disagree.

## 2. What each flag actually does in the app

- **`isBeverage`** feeds the **Beverages slot** on the Plan screen. If an
  item that should be a beverage is missing this flag, it simply never
  shows up there.
- **`isSnack`** feeds the **Snacks & Desserts slot** the same way.
- **`isBreakfast`** (new) feeds the **Breakfast slot** the same way.

**All three flags are now wired up and doing real work in the app today** —
each slot mixes matching recipes together with every item carrying its
flag, ranked together. (Before Sept 2026, `isSnack`/`isBreakfast` existed
only as data with nothing reading them; that's no longer true.)

- **`imageFile`** — a real per-item photo. No item has one yet; see
  `docs/probes/P4-item-images.md` for the file format once you're ready to
  supply images.

**What breaks if a flag is wrong:** if an item is wrongly flagged
`isBeverage: true` (or isSnack/isBreakfast), it can show up in that slot
even though it doesn't belong. If a real beverage/snack/breakfast item is
missing its flag, it's honestly just absent — Remedi never invents an item
to fill a slot, so a gap here means a thinner (or empty) list for the user,
not a wrong item.

## 3. Exactly what to edit, and the format

Open `src/data/cache/itemOverlay.json`. It's a flat object. The key is the
item's `foodItemID` **as a text string** (in quotes), and the value is an
object with whichever flags apply. Here's a real, concrete example using
actual items from the data:

```json
{
  "267": { "isBeverage": true },
  "449": { "isBeverage": true },
  "1319": { "isBeverage": true, "isSnack": false },
  "688": { "isSnack": true }
}
```

Reading that:
- `"267"` is **Soy milk** — `isBeverage: true` because it's a drink (this
  one's already been added, see §7).
- `"449"` is **Tomato juice** — same reasoning (also already added).
- `"1319"` is **Almond Milk** — it already gets `isBeverage: true` from the
  machine guess; you'd only add a line like this if you wanted to also
  explicitly say it's *not* a snack, or override something.
- `"688"` is **Honey** — the machine guess deliberately leaves this
  unflagged (see §5). If you disagree and think it should count as a
  snack, adding this line overrides that decision. Your file always wins.

You only need to add a key for an item you're actually setting a flag on.
Don't add an item at all if you have nothing to say about it — an absent
item is fine, it just means "no opinion yet," not "definitely not a snack."

## 5. Suspected mis-flags — items worth a second look, not necessarily wrong

of them are correct on purpose; a few are worth you double-checking.

- **Items flagged `isBeverage` outside the Beverages group: 22.** This is
  expected — real drinks that live in other Nutridigm groups (orange juice

- **Sweets & Snacks items missing `isSnack`: 8.** These are all ingredients

  confirm you agree.
- **Items flagged `isSnack` outside the Snacks group: 151.** Same story as
  beverages — real snacks (almonds, cashews, dried fruit) that live in
  other Nutridigm groups. Not something that needs fixing.
- **Items flagged `isBreakfast` outside its two expected groups (f, g1):
  0.** Clean today — nothing to fix. (This check exists because
  `isBreakfast` is only ever machine-tagged inside f/g1; anything else
  flagged breakfast could only get there through a hand-edit in
  `itemOverlay.json`, so a nonzero count here would flag your own file for
  a second look, not the machine's.)
- **Conflicts between your file and the machine file: 0** (your file now
  has 2 entries — Soy milk and Tomato juice — and neither disagrees with
  the machine's guess, since the machine pass never touched either item in
  the first place. If you ever add a line that disagrees with the machine's
  value for the same item, the audit script will catch and list it, so you
  can see at a glance what you've overridden).

## 6. Priority ranking — work group-by-group, cheapest-impact-first

Not every missing flag matters equally. The Plan screen currently fetches
food suggestions from **10 specific Nutridigm groups** (the ones any meal
slot draws from) and ignores everything else entirely. So an item outside
those 10 groups — supplements, herbs, lifestyle entries like "Exercise,"
recipes — will never appear in the Plan screen no matter what you flag it,
because the Plan never even asks Nutridigm about that group. Of the 1,202
missing-flag items, **853 fall into that "the Plan never looks here"
bucket** — genuinely fine to ignore.

That leaves two real categories:

- **68 items** live in a group whose flag is live TODAY (breakfast/f,g1,d;
  snacks/h1,c3; beverages/h2) — a missing row here means a real gap in
  what a user could see, not a future one. This is now the priority list;
  see §7.
- **281 items** live in one of the other fetched groups (c2, e, b1, b3),
  but those are the lunch/dinner groups, which only ever show recipes, not
  raw items — so a flag there doesn't change anything a user sees today.

## 7. Top 10 to look at first

One important technical detail: the Beverages slot doesn't only look inside
the "Beverages" (h2) group for drinks — it scans **every** item fetched
for *any* meal slot that day, and pulls in anything flagged `isBeverage`,
regardless of which Nutridigm group it's filed under. That's *why* items
like orange juice (filed under Fruits) and almond milk (filed under Nuts &
Seeds) still show up as real Beverages-slot candidates today (§5's "22
outside h2" list) — and it's why the two items below were the highest-value
things to flag next: they sit in groups the Plan screen already fetches for

## 9. Re-running this audit

Anyone with the codebase can regenerate this entire report, with current
numbers, at any time:

```
node scripts/audit-overlay.mjs          # human-readable
node scripts/audit-overlay.mjs --json   # for tooling
```

It's read-only — it never changes `itemOverlay.json` or any other file. Run
it again after you've made a batch of edits to see the coverage numbers
move and to catch any place your file and the machine file disagree.
